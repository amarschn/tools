# Cam Generator v2

Date: 2026-10-17
Status: Prototypes built on `task/cam-generator-v2`; production direction proposed for review

## Why

The current cam generator (`tools/cam-generator/`) builds a translating in-line
roller cam from a rise/fall/dwell table with four motion laws. It plots SVAJ and
the profile. It does not tell the user whether the cam works. Its README lists
pressure angle and undercut as out of scope, and it gives no help with sizing,
forces or manufacture.

## What was built

Seven prototypes in `tools/cam-generator/prototypes/`, all on one shared engine
(`cam-core.js`). See that folder's README for how to run and test them.

| Prototype | Idea | Verdict |
| --- | --- | --- |
| A: Motion Sketch | Drag keyframes; boundary-condition polynomials fill the spans. Stops, pass-through points, constant-velocity spans, classic laws between stops. | Strongest new idea. Becomes the advanced motion editor. |
| B: Follower Workbench | Animated mechanism with roller (offset), flat-faced and swing-arm followers. Profile colored by check status. Auto-size. | Becomes the main results view. |
| C: Sizing Map | Base circle against offset or roller size, colored by worst pressure angle, failing areas hatched, smallest passing design starred. | Keep as a "Size" tab. Fast (about 9,000 cams in 30 ms). |
| D: Machine Timing | Several cams on one shaft, interlocks, machine speed limit. | Different user and job. Make it a separate tool later. |
| E: Spring & Torque | Jump speed, spring sizing, contact force, cam torque, flywheel. | Keep as a "Forces" tab. |
| F: Law Lab | Laws ranked on the user's rise, with residual vibration. | Fold into the motion-law picker and the Background tab. |
| G: Make It | Plate, grooved and barrel cams; bore, keyway, cutter check; DXF, SVG, CSV, 1:1 print. | Keep as an "Export" tab. |

## Proposed production shape

One tool, five tabs, following Progressive Simplicity:

1. **Motion.** Default is the existing segment table (now with modified sine and
   modified trapezoid). An "Edit as curve" switch opens the A sketcher on the
   same data.
2. **Mechanism.** B's animated view, checks and auto-size. Follower type is a
   first-class input.
3. **Size.** C's map for users who want to see the trade-off.
4. **Forces.** E's jump speed, spring sizing and torque.
5. **Export.** G's drawings and files.

The hero result on load: a passing cam drawn and turning, with the three checks
(pressure angle, curvature, jump speed) as status pills.

## Decision needed: where the equations live

`AGENTS.md` asks for calculations in `pycalcs` with docstrings, so that one
place holds each equation. The prototypes keep the math in JavaScript because
dragging needs results in a few milliseconds, which a Pyodide round trip does
not give reliably.

Recommended: port `cam-core.js` to `pycalcs/cams.py` as the documented,
tested reference (docstrings, LaTeX, tests against textbook values), and keep a
small JS mirror for interaction. A golden-values JSON generated by pytest and
checked by a browser test keeps the two from drifting. The alternative,
JavaScript only, breaks the single-source rule and loses docstring-driven
tooltips.

## Other open questions

- Machine Timing (D) as its own catalog entry, or a mode of this tool?
- Four-bar linkage synthesis came up as a sibling tool for the same motion
  programs. It would reuse A's motion editor. Not started.
- Units: the prototypes are metric only. The production tool should use
  `shared/units.js`.
