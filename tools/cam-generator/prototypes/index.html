Seven ways to design a better cam

The current tool turns a rise/fall/dwell table into a profile. These prototypes ask what an engineer actually needs: say the motion the way the machine needs it, see whether the follower will push, jam, jump or ring, find the smallest cam that works, and leave with a file a shop can cut.

Every prototype runs on one shared engine (cam-core.js) and recomputes on every drag. A design made in one page carries to the next through the "Open in…" buttons.

What the current tool is missing, and which prototype answers it

  • No pressure angle or undercut check. The README lists both as out of scope, yet they decide whether a cam works at all. → B, C
  • No way to size the cam. Base circle is a guess; nothing says it is too small or wastefully large. → C (map), B (auto-size)
  • Only translating in-line rollers. Offset, flat-faced and swing-arm followers are the common cases in real machines. → B
  • Only rest-to-rest segments. Constant-velocity passes and via points can't be described. → A
  • Four motion laws, no guidance. Modified sine and modified trapezoid are the industry workhorses and are missing. → F
  • No forces. Kinematics alone can't tell you the follower will jump at 400 rpm. → E
  • No output. A plot is not a part. → G (DXF, SVG, CSV, 1:1 print)
  • One cam at a time. Machines coordinate several. → D
